Methodology

How every number is produced, what each label means, and where it stops being reliable. OMEN never shows an estimate as a measurement.

Evidence categories

Memory measured: a recorded peak-VRAM run of this exact model, quantization, GPU and GPU count, at your context length or longer, your concurrency or higher, with a KV cache no narrower than yours. Only this earns "Measured to fit".

Performance measured: a recorded decode speed for this setup. It says nothing about memory.

Calibrated estimate: the speed estimate uses measured runs on this GPU for other setups.

Estimated: first-principles maths only.

Memory

Weights = parameters x bytes per weight (including quantization scales). KV cache per user = 2 x layers x KV heads x head size x bytes per element x context. It fits when weights + overhead + users x KV is within VRAM.

KV cache type: fp16 and bf16 use 2 bytes, fp8 and int8 use 1 (per-tensor scales assumed; the quality impact is not measured by OMEN).

Sliding-window models (Gemma, gpt-oss, Mistral-7B and others whose config.json says so) keep only the window in their local layers. OMEN assumes a full cache unless you say your engine frees it, because many engines do not.

MLA models (DeepSeek, Kimi) use an effective head size matching their compressed cache. Chunked attention (Llama 4) is not modelled and is overestimated at long context.

Speed

Decode ceiling = memory bandwidth / bytes of weights read per token (active parameters for MoE). It is an upper bound, not a prediction.

Expected speed = ceiling x a measured ratio. The ratio is taken only from runs that match your workload: the same number of users and a context within 4x of yours, on this GPU and engine first. Runs at other concurrency or context are never averaged in. If none match, OMEN steps down to this GPU at your concurrency but a different context, then other GPUs, then (when nothing anywhere matches your concurrency) the nearest hardware's runs as they are. Every step down is labelled "extrapolated". OMEN shows how many of the runs on that hardware were used, their range, and which models, quantizations, contexts and concurrency they covered. Only a matched same-GPU sample escapes "extrapolated", and with fewer than 3 runs it says "thin".

The ceiling ignores the KV-cache reads each step, so long contexts and many users run slower than it implies. Time to first token assumes 40% of peak compute and is uncalibrated.

Quality loss and GPU specs

Quality loss is the perplexity increase vs fp16. Measured means a recorded perplexity on one model (Q4_0, Q5_0 and Q8_0 on Llama-2-7B). ~N% is a typical value, estimated. Unknown means it varies too much to give a number; an unknown cannot pass a quality limit.

GPU VRAM, bandwidth and TFLOPS are marked verified only where OMEN read them from a vendor page or datasheet (with the date). Everything else was written from memory and is flagged unverified.

Known limits

Multi-GPU pooling uses a flat 0.85 bandwidth factor, not your interconnect. Prices are assumptions unless a recorded price is used. Benchmarks so far are few and cover one model on one engine, so error figures do not transfer to other setups. Always benchmark your own configuration before buying.
